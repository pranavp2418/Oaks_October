# Engineering directions for future projects

Effective October 8, 2026. This reference captures the October 7 user follow-up and supplements the existing build brief. Choose the concept, industry and implementation autonomously. Preserve the existing requirements for three distinct complete projects, two resume-grounded stacks and one substantive new core technology, private inspiration research, delivery mix, verification, sequential source releases and both portfolio presentations.

## Selection standard

Prioritize a useful problem whose solution exposes serious engineering: custom algorithms, storage or runtime internals, distributed failure handling, ML mathematics, secure execution, retrieval quality, developer productivity or a measurable business workflow. Rotate these directions across the collection. A day may mix systems, AI/ML and product engineering when the strongest researched opportunities support it; there is no fixed requirement for one of each category.

Each candidate needs a concrete user, input/output contract, substantive core, boundaries, failure model, verification plan and complete delivery path. Challenge it against previous projects for problem, algorithm, architecture, stack and visual similarity. Select the strongest three materially different candidates. Implement the essential core and the connected workflow; dependencies must have a clear purpose. Source-line count, buzzwords and extra infrastructure do not establish engineering depth.

## Depth and verification gate

Before implementation, record the core technical contribution and the invariants that make it trustworthy. Give it meaningful tests with independent reference implementations, exact/brute-force oracles, gradient checks, replay fixtures or fault injection as appropriate. Exercise invalid input, corruption, interruption, retry, concurrency, resource exhaustion and recovery where they are part of the model. Document persistence and consistency semantics explicitly.

For performance-oriented work, include a runnable benchmark with dataset seed/size, hardware, OS, compiler/runtime versions, build flags, warmup, repetitions and measurement method. Compare with a suitable baseline; report correctness, throughput, latency distribution and memory when relevant. Distinguish a measured result from a target. Do not copy example claims such as sub-100ns matching, sub-millisecond guards, zero-overhead tracing, millions of IOPS or 90% hardware peak into results without evidence. Likewise do not label a concurrency design lock-free, a service highly available or a product production-ready without the relevant design proof and tests.

Keep scope deep and runnable on available resources. GPU kernels, multi-GPU training, raw-NIC/kernel bypass, eBPF, direct disk I/O, embedded control and native distributed services need suitable hardware/runtime and permissions for their claimed measurements. A software simulation must be clearly identified and evaluated as a simulation. Choose a viable project/deployment architecture during ideation; preserve exact blockers if essential execution cannot be verified. Never replace an essential core with a fake endpoint or count untested hardware claims as a finished project.

Use the existing roughly 90% deployed/10% GitHub-only policy. A complete native engine, CLI, library or kernel may fit a planned GitHub-only slot. Deployed projects need their real core running through supported APIs, WASM or another verified runtime integration. A visual sandbox can explain a real engine, but must not imply unsupported persistent servers or hardware capabilities. Preserve advanced local checks for every delivery mode and live/browser checks for deployed products.

For founder work, choose a concrete operational pain and demonstrate the business workflow and cost assumptions. Do not invent customers, revenue, community adoption, compliance certification or product-market fit. Security monitoring produces findings and evidence, not automatic certification. Do not introduce paid resources or publish outbound messages solely because a growth-oriented example suggests them.

Finance/quant, healthcare/RCM and education/edtech still require at least two substantial connected capabilities beyond the main core. Maintain clear synthetic-data provenance and honest limitations. Finish documentation, tests, reproducible examples, complete code and applicable UI; verify and release each project in completion order. Only then integrate the completed daily set into both the existing portfolio archive and separate Projects country.
