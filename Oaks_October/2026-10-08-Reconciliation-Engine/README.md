# Operations Reconciliation & Pricing Analysis Engine

A working close workspace for reconciling book and bank records, inspecting historical prices and valuing inventory with FIFO lots. This completes the previously descriptive portfolio entry with a deployable Python core and a usable review workflow.

- [Live workspace](https://reconciliation-engine-pranav.vercel.app/)
- [Source](https://github.com/pranavp2418/Oaks_October/tree/main/Oaks_October/2026-10-08-Reconciliation-Engine)

## Walkthrough

1. Open the synthetic close. Fourteen record pairs match automatically, one duplicate is ignored and equal-optimum pairings remain unresolved.
2. Change the date window or cent tolerance and recompute. Inspect each pair's difference and evidence. A two-cent tolerance admits the sample's small mismatch.
3. Choose an exception. Add an owner and note, assign or review it, or choose a same-account/currency counterpart for a reviewed match. Differences remain visible. Unmatching blocks that specific automatic edge.
4. Inspect historical unit prices. The SQLite lookup uses the most recent price effective **on or before** the movement, never a future price.
5. Inspect FIFO inventory. An issue consumes oldest receipts first. A shortage quarantines the entire issue without consuming any lots. Remaining units, ages, exact historical costs and issue allocations are visible.
6. Inspect the audit journal, export it, reload the page and import it to replay the same state. Import validated JSON or two CSV transaction lists. CSV exports escape formula-leading strings.

## Core and architecture

Python's standard library performs the actual server-side work; the browser has no alternate scoring or matching implementation. `/api/compute` validates the bounded request, rebuilds the model and returns projections plus a matches CSV. Amounts are decimal **strings**, converted with `Decimal` into integer cents. There is no floating-point arithmetic in the reconciliation or valuation core.

Automatic reconciliation is a maximum-cardinality, minimum-weight-cost bipartite matching problem. Successive shortest augmenting paths use residual reverse edges and Bellman–Ford to reroute earlier choices. Cost is `date_gap * 10001 + abs(cent_difference)`; this is a weighted cost, not a globally lexicographic date objective. Removing each chosen edge and solving again detects alternative equal optima. Those pairs are withheld for human review. Matching never crosses account or currency boundaries, and confirmed pairs are one-to-one.

SQLite's composite primary key indexes SKU/effective-date pricing. A deterministic FIFO deque allocates inventory lots in movement-date/ID order. Exact inventory valuation is a separate USD sample workflow; transaction totals stay grouped by currency and are never added across currencies. Reviewed exceptions are labels for investigation, not financial adjustments or inventory corrections.

Each browser workspace stores the dataset, policy and operation journal in local storage. A request replays the journal; the Python process is stateless, and SQLite is intentionally in memory. Operation keys prevent duplicate effects, conflicting key reuse fails, and expected revisions reject stale writes. Web Locks serialize writes in supporting browsers; a storage listener reloads sibling tabs. Without Web Locks, concurrent tab writes can still overwrite one another: export before sharing work between tabs. SHA256 hash chains plus an exported head detect changed exports when compared, but do not prove authorship or prevent a malicious user from recomputing a chain. This is not a shared, authenticated financial system.

## Stack

Python 3.12+, SQLite, Decimal, minimum-cost flow, FIFO lot allocation, vanilla JavaScript, SVG, semantic HTML and responsive CSS. Vercel's Python function hosts the real core. No external AI, banking API, database subscription or paid integration is required.

## Dataset, schema and assumptions

`data/sample.json` is generated by `scripts/generate.py`, seed **8102026**, valuation date **2026-10-08**. It contains 18 unique fictional book records, 18 bank records, one identical duplicate book row, historical price entries and six inventory movements. All references, accounts and quantities are invented. No customer, patient or bank data is present. The original SVG cover is generated for this project. The project and its synthetic data are released under MIT; no third-party dataset attribution is required.

Transactions require `id`, `reference`, `date` (YYYY-MM-DD), `account`, three-letter uppercase `currency`, and `amount` (decimal string, at most two fractional digits). Prices require `sku`, `date`, `price`; movements require `id`, `sku`, `date`, `type` (`receipt`/`issue`), integer `quantity`, and `unitCost` (decimal string). Same-date inventory movements are ordered by ID. Matching requires exact normalized alphanumeric reference plus account/currency equality and bounded date/amount tolerance. Split, many-to-one and fuzzy-reference settlement are outside this release.

Bounds: 60 rows per transaction side, 120 prices and movements, 300 journal operations, 1 MB request body, 0–30-day date window and 0–10000-cent tolerance. Policy or dataset changes can invalidate earlier exception operations; the backend rejects those replays and preserves the existing browser workspace rather than silently changing a decision. Use a fresh workspace for a substantially changed dataset.

## Verification

`npm test` runs **14 meaningful core/API tests**, including 80 seeded small graphs compared with an exhaustive matching oracle, a residual rerouting case, equal-optimum holdback, one-to-one constraints, deduplication, exact cents, currency/account isolation, historical-price lookahead exclusion, FIFO conservation and shortage quarantine, review replay, idempotent retries, stale revisions, invalid inputs, CSV validation and formula escaping. HTTP integration tests exercise the real Python handler with 200/400/405/409 responses. Clean install and static build are checked separately. Actual live/browser verification and deployment IDs are recorded in `RELEASE.json` after verification; no throughput or production-scale claims are made.

## Limits

Use fictional data only: supplied datasets are sent to this public demonstration endpoint. There is no authentication, centralized persistence, bank connector, automated payment, spreadsheet VBA runtime, LLM call or multi-user approval system. CSV import replaces the current sample with transaction-only data after validation. Exports are the backup mechanism. Matching uses bounded demonstration data, not a claim of real financial accuracy or readiness for regulatory use. The UI is responsive and keyboard accessible; data tables scroll within their containers on narrow screens.
