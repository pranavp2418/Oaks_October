# Gstack workflow

Apply the user's selected gstack methodology (https://github.com/garrytan/gstack) rigorously throughout software development. Tool availability and permissions remain governed by the host environment.

## Installation and compatibility

Use the installed gstack Codex skills where available. Read the relevant installed SKILL.md before applying a workflow. If missing, consult the official repository installation guidance and report the prerequisite; this skill does not execute an automatic installer. Codex support is experimental. Preserve the configured model and follow host permissions and approval requirements for every action.

## Execute

1. Read current repository instructions, actual progress and user constraints. Search for existing helpers, standard library, platform features and installed dependencies before adding code.
2. For substantive functionality, use office-hours/plan-ceo-review to challenge the product, then plan-eng-review for architecture, data invariants, failure recovery and tests. Use plan-design-review for UI work and eval-plan for AI/retrieval work. Resolve design choices from the current task requirements; clarify material ambiguity as needed.
3. Implement complete connected workflows with honest skill evidence, meaningful edge cases, persistent-state behavior and integration tests. Use investigate for root-cause debugging.
4. Use review and test-audit before release. Apply cso/security review for authentication, tenant boundaries, ingestion, financial data, tools and AI inputs; report unavailable scanners explicitly.
5. Use qa/qa-only and design-review for applicable desktop/mobile/keyboard flows, API/CLI jobs and failure paths. Follow higher-priority tool/browser rules. If gstack's browser cannot run, preserve its QA methodology with the permitted browser and disclose the substitution.
6. Use ship/document-release for scoped authorized releases. Run real builds/tests, inspect CI, verify deployed source and user workflows, and retain reproducible evidence. Cross-model consensus is never a substitute for tests or permission.
7. Report workflows used, actual findings/fixes, verification and blockers. Do not inflate completion, confidence or skill coverage from dependency lists or tool invocation alone.

Preserve accepted scenery and performance improvements, keep independent-project dates hidden, leave CraftsmanAI's timeline intact, and never publish the declined island redesign. Keep both flagships additional to the daily three. Apply this workflow to existing and future software project work without silently widening scope.

## Daily project UI — standing user requirement

Use Motion Primitives (https://motion-primitives.com) for polished React interaction primitives, Haikei (https://haikei.app) for intentional SVG visual assets, and Realtime Colors (https://www.realtimecolors.com) for palette/typography exploration and token export. Verify current official documentation and licensing before incorporation. For non-React projects, preserve the chosen stack and implement equivalent native motion rather than adding React only for animation.

Define a distinct art direction per project before coding: audience, references, grid, typography scale, spacing, palette, component states and motion specification. Avoid repeating the same dashboard, generic purple gradients, decorative blobs or card-grid hero across projects. Use Haikei assets where the product benefits, not as automatic decoration. Test colors on actual screens, including dropdown menus, disabled controls, charts and hover/focus states; target readable AA contrast.

Design coordinated navigation, layout/shared-element transitions, drawers/dialogs, loading/progress, charts and meaningful completion/error feedback. Give motion consistent easing, durations and spring behavior. Preserve reduced-motion alternatives, keyboard access and immediate input response; prefer transform/opacity, pause offscreen effects and measure representative mobile performance. Do not trade useful workflows for animation volume.

Require gstack design planning, design-review and QA with desktop/mobile screenshots of complete workflows before release. Record references, palette tokens, animation behaviors, actual asset/component provenance, accessibility checks and measured performance. Disclose when a named tool was inaccessible; locally authored equivalents must not be mislabelled as outputs of that tool. This strengthens future daily project UI and flagship interfaces; it does not authorize replacing the accepted portfolio island design.
