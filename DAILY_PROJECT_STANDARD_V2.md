# Daily project standard v2

Effective October 13, 2026. The user asks for substantially larger functionality and engineering complexity, real coverage of the supplied LinkedIn skills, and additional currently demanded skills. This supplements the existing three-project instructions; it does not remove uniqueness, two resume-grounded / one substantive new stack, two private hiring-company inspirations, delivery mix, publishing, evidence, or portfolio preservation rules.

## Acceptance contract before coding

Describe the problem, actors, real workflow, data/storage boundary, custom technical contribution, invariants, functional capabilities, integration dependencies, failure modes and deployment path. Challenge the concept against every earlier project. Reject a renamed or shallow variant.

A product must have at least six connected meaningful capabilities: its advanced core, import/persisted state, a multi-step operational or review workflow, failure recovery/reprocessing, evidence/export, and useful operational or performance inspection. Native tools/engines need equally substantive CLI/API workflows. Finance, healthcare and education retain the two additional domain-depth capabilities. More pages, code lines, dependencies or mock services are not complexity evidence.

## Engineering scorecard

Record passed/blocked/not-applicable with file and test evidence for each axis:

1. Custom core algorithm or state model with a reference/oracle or invariant checks.
2. Durable data/persistence, schema evolution and transactional boundaries appropriate to the product.
3. Real API/component integrations, contracts, repeated requests and authorization where required.
4. Failure handling: retries, idempotency, recovery, concurrency or corruption, with adversarial tests.
5. Performance/data quality: reproducible load, query-plan or algorithm evaluation tied to the actual design.
6. Complete user/operator workflow, accessible interface or usable CLI and clear operational evidence.
7. Reproducible build, source, real deployment/runtime verification and recovery documentation.

Do not mark an axis passed from a README assertion. Specify any not-applicable judgment; do not use it to excuse core gaps. A multiuser web claim requires real remote/database persistence and access boundaries. Browser-local state may be used in an honestly single-user model but is not proof of a shared system.

## Skill coverage

Normalize the supplied skills using SKILL_EVIDENCE_MATRIX.json. Keep earlier resume/profile skills. Prioritize high-value unsupported gaps during selection; update the rolling seven-run review with skill → implementation → verification → limitation links. Existing archive labels do not prove skill use or LinkedIn association. Audit source before claiming prior coverage. Newly demanded skills must have dated primary hiring/engineering evidence and a concrete product role.

Kafka/PostgreSQL/cloud/container/Jenkins/LLM claims require the actual integrated technology to run. A dependency import, adapter stub, Dockerfile or Kubernetes YAML alone is planned configuration. Query optimization needs EXPLAIN ANALYZE and before/after correctness/workload evidence. Performance claims need environment, size/seed, warmup, repetitions, distributions and a proper baseline. LLM and predictive capabilities need evaluation/failure handling and real outputs; a chat box or hardcoded scores do not qualify.

Use skills where they fit the product. Rotate Java/Spring Boot, Angular, C/C++, Express/React, Python/SQL, AWS/Kafka and earlier skills rather than continuously using the same TypeScript/Python mini-demo. Do not force the entire list into each project. Do not add unneeded microservices or another language for visual complexity.

## Completion and reporting

Three complete new projects remains the daily target. The bar is not lowered if the run is late. Report the actual count and blockers; retain and resume unfinished work without duplicate counts. Check unit/core, actual integration/end-to-end and failure paths, clean build/install, live workflows and source identity. Preserve all earlier site content, no independent-project dates, working dropdown contrast and latest island performance improvements.

The AsterLedger/ForgePulse long-horizon projects in pranavp2418/AtlasForge are separate additional work. Read their PROGRESS.json and latest run report in the daily final confirmation. Report both flagships' actual changes/tests/commits, milestone gates, blockers and next actions; no new verified work must be stated plainly. Do not count either flagship or its maintenance slices among the daily three.
